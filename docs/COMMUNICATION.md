# Communication — Мережевий транспорт Old Kraken

Цей документ описує внутрішню роботу транспортного модуля `Communication.lua` та протоколу обміну повідомленнями між клієнтами аддона в гільдії.

---

## 1. Канал та префікс

- **Канал:** `GUILD` (уся комунікація здійснюється виключно всередині гільдії).
- **Префікс повідомлень:** `OLDKRKN`.
- Реєстрація префікса виконується під час `PLAYER_LOGIN` через `C_ChatInfo.RegisterAddonMessagePrefix`.

---

## 2. Формат кадру (`GF2`)

Повідомлення кодуються у форматі з розділювачем `^`:
```text
GF2^KIND^ID^PART^COUNT^HEX
```

- **`GF2`** — версія кадру протоколу.
- **`KIND`** — тип повідомлення (із закритого переліку `VALID_TYPES`).
- **`ID`** — унікальний ідентифікатор передачі (`sessionID-messageSequence`, де `sessionID` генерується на старті сесії).
- **`PART`** — порядковий номер фрагмента (1..COUNT).
- **`COUNT`** — загальна кількість фрагментів (1..32).
- **`HEX`** — шістнадцятковий payload (кожен байт як `%02X`), що зберігає кодування UTF-8 і не конфліктує зі спецсимволами.

---

## 3. Ліміти та параметри черги

| Параметр | Значення | Опис |
|---|---|---|
| `PART_BYTES` | 80 байтів | Максимальний розмір корисного навантаження в одній частині |
| `MAX_PARTS` | 32 | Максимальна кількість частин для одного повідомлення |
| **Максимальний payload** | **2560 байтів** | 80 байтів × 32 частини |
| `MAX_FRAME` | 240 байтів | Максимальний розмір одного рядка повідомлення для чат-системи WoW |
| `MAX_QUEUE` | 4096 | Максимальна місткість черги вихідних повідомлень |
| `ACTION_RESERVE` | 256 | Зарезервовані слоти для високопріоритетних дій (пріоритет 0) |
| `BACKGROUND_LIMIT` | 3584 | Поріг черги для фонових повідомлень (`MAX_QUEUE - ACTION_RESERVE`) |
| `CACHE_TTL` | 120 с | Час життя дедуплікаційного кешу для запобігання обробці дублікатів |

---

## 4. Пріоритети черги та обробка

1. **Пріоритет 0 (Дії):** критичні транзакції та рішення (заявки в групу `JOIN`, `RESPONSE`, скасування `CANCEL`, RSVP на події `CEVRSVP`, дії замовлень `WOREQ`, `WOACT`, `WOPAY`).
2. **Пріоритет 1 (Знімки):** стани та оголошення (`ANNOUNCE`, `UPDATE`, `WORDER`, `CVNEW`, `CVSTATE`).
3. **Пріоритет 2 (Фонові запити):** синхронізація, каталоги, пінг (`QUERY`, `WKQUERY`, `WRQUERY`, `WRIDX` тощо).

**Тікер вибірки з черги (`Pump`):** кожні 0,7 секунди надсилає наступний доступний пакет із найвищим пріоритетом.

**Обробка невдач (Backoff):** при помилках чи тротлінгу API повідомлення залишається в черзі з експоненційним backoff (2, 4, 8... до 60 с) з додаванням джиттера.

---

## 5. Безпека та верифікація відправника

- Аддон не використовує зовнішні сервери для авторизації.
- Кожне повідомлення перевіряє повноваження відправника (`sender-authority`):
  - Зміни в групі приймаються лише від власника оголошення (`sender == owner`).
  - Зміни в календарі подій приймаються лише від автора події.
  - Заявки приймаються лише від самого заявника.
- Для пересланих повідомлень (офлайн-релей) діє обмеження: пряме оновлення від автора завжди перезаписує пересланий стан.

---

## 6. Протокол спеціалізацій (`SPEC1` та `SPEC2`)

На відміну від фрагментованого транспорту `GF2`, повідомлення спеціалізацій `OKP^SPEC^` (`SPEC1`) та `OKP^SPEC2^` (`SPEC2`) передаються через канал `GUILD` як окремі короткі повідомлення (`<= 240` байтів) без `GF2`-обгортки та потребують встановленого аддона на обох сторонах.

### Формати та валідація
- **Legacy `SPEC1` (`OKP^SPEC^<specID>`):**
  - `<specID>` — ціле число `1..9999999`.
  - Зберігається в парсері лише для сумісності зі старими клієнтами без збільшення `stats.invalid`. Не перезаписує свіжий запис або tombstone `SPEC2` протягом `3600` секунд; після протухання цього запису (`> 3600` с) legacy `SPEC1` може бути записаний у `rosterSpecs` (HWM `SPEC2` зберігається окремо і не блокує запис `SPEC1`).
  - `GetRosterSpec()` не відображає legacy `SPEC1` у UI (оскільки `GetSpecializationInfoByID` у цільовому клієнті повертає лише базові класові заглушки на кшталт `1485 = Hunter`).
- **Актуальний `SPEC2` (`OKP^SPEC2^<seq>^<icon>^<points>^<name>`):**
  - `<seq>` — монотонний порядковий номер (`1..999999999999`).
  - `<icon>` — числовий `fileID` текстури (`0..999999999`, де `0` означає відсутність іконки).
  - `<points>` — розподіл очок за трьома гілками `a/b/c` (`0..999` на кожну гілку).
  - `<name>` — назва активної гілки (`1..64` байтів валідного UTF-8 без `^`, `|` та керуючих байтів) або порожнє поле `name` для канонічного reset.

### Локальні стани (`ACTIVE` / `RESET` / `UNKNOWN`)
- **`ACTIVE`:** `sig.spent > 0`, усі 3 UI-заголовки `PlayerSpellsFrame.TalentsFrame.treeHeaders` валідні, `a + b + c == sig.spent` і є єдиний строгий максимум серед трьох гілок.
- **`RESET`:** визначається **виключно** за авторитетним підтвердженням `sig.spent == 0` через `C_Traits`; формує канонічний reset payload `0^0/0/0^`.
- **`UNKNOWN`:** `sig == nil`, нічия розподілу (`10/10/0`, `5/5/5`), розбіжність `a + b + c ~= sig.spent`, `secret` або недоступні UI-дані. Не трактується як `RESET` і ніколи не породжує `0^0/0/0^`.

### Захист порядку, Tombstone та High-Water Mark (`roster.specSequences`)
- **Правила `seq`** (однаково для `ACTIVE` і `RESET`):
  - `seq < hwm.seq` — відхиляється без зміни стану.
  - `seq == hwm.seq` з ідентичним payload — повторна доставка (оновлює `receivedAt` лише якщо запис у `rosterSpecs` ще активний, без `ROSTER_ADDON_CHANGED`).
  - `seq == hwm.seq` з іншим payload — конфлікт, відхиляється без зміни стану.
  - `seq > hwm.seq` — приймається після валідації.
- **Tombstone:** отримання `0^0/0/0^` зберігає у `rosterSpecs[key]` запис із `reset = true` (TTL `rosterSpecs` / tombstone — `3600` с) замість негайного очищення, щоб протягом цього вікна блокувати затримані legacy-пакети `SPEC1`.
- **High-Water Mark (`db.roster.specSequences`):** ключується як `realm\001guild\001senderKey`, зберігає `{ seq, payload, updatedAt }` незалежно від 3600-секундного TTL `rosterSpecs` (це окремий механізм захисту порядку `SPEC2` від старіших/конфліктних пакетів). Обмежений `1024` записами; записи HWM вважаються простроченими після `30` днів (`2592000` с) і видаляються під час наступного звернення до відповідного ключа або під час очищення при досягненні ліміту `1024` записів (якщо після видалення прострочених записів ліміт усе ще перевищено, видаляється найдавніший запис за `updatedAt`).
- **Межі гарантій:** `SavedVariables` у WoW записуються на диск лише при `/reload` або чистому виході з гри, тому **не є crash-durable**; захист від replay обмежений вікном зберігання (`30` днів), лімітом ключів (`1024`) та можливим розсинхроном після аварійного завершення клієнта.

---

## 7. Діагностичні команди

- `/okr comm status` — виводить у чат стан черги, доступність API, лічильники надісланих, отриманих, відкинутих і недійсних пакетів.
- `/okr comm test` — надсилає пінг у канал гільдії; клієнти з аддоном автоматично відповідають ACK, підтверджуючи двосторонній зв'язок.
