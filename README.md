# Old Kraken Guild Addon

## Мова інтерфейсу та назва гільдії

У головному вікні `/okr` відкрийте **Налаштування** та виберіть **Українська**
або **English**, потім натисніть **Застосувати й перезавантажити**. Українська
використовується за замовчуванням. Мова спільна для персонажів на акаунті.

Заголовок і бічна панель показують поточну гільдію персонажа. Коли WoW
не повертає назву гільдії, вони показують **Old Kraken**.

## Майстерня — каталог професій (у розробці)

Відкрийте `/okr workshop` або кнопку «Майстерня» в ростері. Картка професії відкриває вкладки «Рецепти» та «Майстри»: у списку майстрів є пошук за ім'ям, фільтр онлайн, рівень професії і дата оновлення, якщо вони відомі. Вибраний майстер доступний для шепоту та перегляду його збережених рецептів. Кожен персонаж створює власний знімок, який інший учасник може передати через `OLDKRKN`; при відкритті аддона й за кнопкою «Оновити» надсилається запит до гільдії. Дані зберігаються окремо для гільдії та realm, тому офлайн-запис може бути застарілим. Для обміну даними учасникам потрібна оновлена версія аддона.

Професії, рецепти, майстри й замовлення відкриваються в Майстерні всередині Hub. Кнопка «Назад» повертає до попереднього перегляду зі збереженим пошуком, фільтрами та вибором. Під час вибору рецепта для замовлення введені у форму дані зберігаються; вибір рецепта або повернення назад відкриває ту саму форму.

Майстерня показує картки з іконками та, якщо клієнт їх надає, ігровим оформленням професій. Клік по картці відкриває збережені рецепти та запитує їх у онлайн-учасників з Old Kraken. У ростері значки біля імені відкривають рецепти конкретного персонажа. Якщо ігровий API гільдії надає основні професії гравця без аддона, показано тьмяні значки без непідтвердженого рівня чи списку рецептів; доступність цього API у Forever ще потрібно перевірити в грі.

Збір професій використовує `GetProfessions` і `GetProfessionInfo`. Зменшення списку застосовується після трьох однакових зчитувань протягом щонайменше шести секунд і не раніше ніж через 15 секунд після входу. Для порожнього списку додатково потрібне підтвердження входу та доступності персонажа. Недоступні або некоректні дані не стирають попередній запис. Після підтвердженого забування професії видаляються також її збережені рецепти. Повноту та готовність API в конкретному клієнті неможливо гарантувати лише повторними зчитуваннями, тому поведінку ще потрібно перевірити у WoW Forever 1.60.1 build 70938.

Кнопка «Пошук рецептів» у Майстерні або `/okr recipes` відкриває пошук майстрів. Для початкового зчитування майстер відкриває **власне** вікно кожної професії та чекає кілька секунд: аддон зберігає лише рецепти, які гра позначила як вивчені. Відомий акаунту каталог допомагає іншим персонажам відновити рецепти, які їхня книга заклинань підтверджує як вивчені; якщо даних немає, потрібно відкрити професію. Після `NEW_RECIPE_LEARNED` аддон намагається зчитати рецепт і повідомити гільдію. Пошук приймає назву рецепта чи предмета або посилання на предмет і запитує онлайн-гравців. Текстовий пошук отримує до 12 збігів від кожного, а запит професії передає рецепти пакетами за наявності місця в черзі. Список і кеш обмежені; відповіді можуть надходити із затримкою.

Вікно рецепта показує іконку предмета, збережених майстрів, дату та матеріали, якщо ігровий API повернув схему. Звідти можна написати майстру або відкрити форму замовлення з обраним рецептом. Дані безпосередньо з інших аддонів не читаються.

Збережені професії та рецепти синхронізуються з учасниками гільдії. Посередник може передати останній знімок офлайн-майстра, отриманий від нього безпосередньо; дані, отримані від іншого посередника, далі не пересилаються. Знімок рецептів збирається частинами й застосовується лише після отримання всіх частин; підтверджені видалення передаються окремими позначками. Новіший стан не замінюється старим повідомленням. Знімок обмежено 5000 записами разом із позначками видалення; передавання може тривати довго. Посередник не надає криптографічного підтвердження походження даних.

Рецепти зберігаються на комп'ютері кожного гравця в `OldKrakenDB`, окремо за realm, гільдією та повним іменем персонажа. Орієнтовний файл для встановленого аддона: `World of Warcraft/_forever_/WTF/Account/<акаунт>/SavedVariables/OldKraken.lua`. Гра записує SavedVariables під час `/reload`, виходу з персонажа або гри; до цього зміни перебувають у пам'яті клієнта. Отримані рецепти інших майстрів також кешуються локально. Зовнішнього сервера немає.

Перелік може бути неповним через фільтри, недоступний API або офлайн-гравців. Рецепт видаляється лише якщо готове власне вікно професії тричі поспіль показало його як невивчений у повному списку `GetAllRecipeIDs`; відфільтрований, порожній чи неповний результат цього не робить. Якщо необхідні API недоступні, старий запис залишається. Записи професій і рецептів старші за 7 днів позначаються як застарілі; невідома дата позначається окремо. Зчитування, видалення й синхронізація ще потребують перевірки у грі.

Замовлення доступні у вкладці «Замовлення» в Майстерні або через `/okr orders`; кнопка «Нове замовлення» відкриває форму. Її також можна заповнити з вікна рецепта кнопкою «Замовити». Замовник обирає рецепт, кількість, винагороду в цілих золотих, ресурси й термін та за потреби додає коментар. Майстри пропонують допомогу; замовник обирає одного з них. Виготовлення, передачу предмета й оплату гравці здійснюють самостійно в грі.

Аддон відстежує підтверджений грою обмін і пошту між замовником та обраним майстром. Для замовлень із ID предмета він рахує часткову передачу готових речей; матеріали — коли доступна схема рецепта, оплату — в мідяках. Прогрес зберігається локально і показується в деталях. Одна передача розподіляється між відповідними замовленнями за часом створення, без повторного зарахування. Після повної передачі майстер автоматично надсилає позначку «Передав»; замовлення завершується після отримання всіх речей і підтвердження майстром отриманої винагороди. Ігровий обмін не означає автоматичного створення торгівлі чи надсилання пошти.

Автоматичний облік залежить від доступних у клієнті подій, ідентифікаторів і схеми рецепта. Замовлення без ID предмета, матеріали без доступної схеми, пересилання через іншого персонажа та неоднозначні поштові оновлення можуть потребувати ручних кнопок. Якщо кілька замовлень мають однаковий предмет і учасників, аддон не може знати намір гравців та зараховує передачу найстарішому. Ці сценарії ще треба перевірити у WoW Forever на двох клієнтах.

У формі замовлення кнопка «Обрати рецепт» відкриває збережені результати пошуку з фільтром професії: клік на рецепт іншого майстра заповнює предмет і професію та прив'язує їхні ідентифікатори. Власний рецепт позначено у списку; створити замовлення з його рядка не можна. Саме замовлення залишається відкритим для гільдії, а не призначається автоматично вибраному майстру. У деталях такого замовлення показано збережених відомих майстрів і дату зчитування; кнопка «Майстри» відкриває їхній список і запитує оновлення в гільдії. Раніше створені текстові замовлення залишаються доступними, але точне зіставлення для них недоступне. Наявність у списку означає, що майстер знав рецепт під час останнього зчитування, а не гарантує його доступність або наявність ресурсів зараз.

Незавершена форма зберігається локально як чернетка окремо для персонажа й гільдії та відновлюється після звичайного `/reload` або повторного входу. Чернетка не публікується і не надсилається гільдії; після успішного опублікування вона очищається. Гра записує SavedVariables під час `/reload` або штатного виходу, тому при аварійному завершенні останні зміни можуть не зберегтися. У виборі рецепта «Скасувати вибір» повертає до форми без зміни чернетки.

Замовник є джерелом остаточного стану. Якщо він офлайн, інший учасник гільдії може отримати безпосередньо від майстра та зберегти його відгук, відмову, позначку передачі чи підтвердження отриманої оплати, а згодом передати замовнику. Результат дії та оновлений стан можуть повернутися через посередника, коли майстер знову онлайн. Поки замовник не обробив дію й не надійшло підтвердження стану, вона залишається в очікуванні; повтори та застарілі призначення перевіряються за версією. Кеш окремо обмежений тисячею записів на тип, до 30 днів; запити й повтори надсилаються приблизно раз на три хвилини з урахуванням черги.

Посередник має отримати повідомлення безпосередньо від відправника і пізніше бути онлайн разом з отримувачем. Отримані від іншого посередника дії та результати далі не пересилаються. Якщо під час відправлення ніхто з учасників з оновленим аддоном не був онлайн, передача чекатиме повторного входу відправника. SavedVariables фізично записуються грою під час `/reload` або штатного виходу. Стан замовлення також може передаватися через учасника, який отримав його безпосередньо від замовника; у деталях такий стан позначено як потенційно застарілий. Прямий стан замовника має пріоритет, якщо він не старіший за останній безпосередньо отриманий. Замовлення зберігаються до 30 днів; знімок обмежено 2560 байтами, а кількість учасників одного замовлення — 20. Усім потрібна оновлена версія аддона.

Пересилання довіряє учасникам гільдії: протокол не має криптографічного підтвердження автора пересланого стану, дії або результату. Інший учасник може підробити повідомлення від імені майстра чи замовника; перевірка версії, одержувача та призначення не усуває цей ризик. Пряма інформація замовника має пріоритет над пересланим станом.

Замовлення показано сіткою карток із предметом або значком професії, замовником, кількістю, винагородою, терміном і статусом. На картці відкритого замовлення можна натиснути «Запропонувати допомогу»; доки замовник не відповів, показано стан очікування. На власній картці видно відгуки; кнопка «Обрати виконавця» відкриває повний список і дозволяє обрати майстра без переходу в деталі. Клік по самій картці відкриває деталі та інші доступні дії. Доступні режими «Усі замовлення», «Доступні мені», «Мої замовлення» та «Моя робота», фільтри стану й професії та пошук за предметом або замовником. «Доступні мені» показує відкриті замовлення без простроченого терміну, на які персонаж ще не відгукнувся: за збігом ID предмета або рецепта, а для текстових замовлень — за збереженою професією. Збіг лише за професією не підтверджує знання рецепта.

Майстер може натиснути «Передав» прямо на картці замовлення в роботі або «Відмовитися», щоб відкликати пропозицію чи відмовитися від роботи. Замовник може скасувати незавершене замовлення зі своєї картки; після отримання позначки передачі також з'явиться кнопка «Отримано». Усі чотири дії з картки потребують підтвердження. Поки дія майстра очікує синхронізації із замовником, картка показує очікування.

Кошик на власній картці видаляє замовлення зі списків після підтвердження, зокрема вже виконане чи скасоване. Стан видалення синхронізується з гільдією та зберігається до завершення строку зберігання замовлення. Учасникам активного замовлення надходить сповіщення про скасування.

Про нове замовлення банер і чат сповіщають майстрів, у яких збережено відповідний рецепт; звук лунає за доступності. Для текстового замовлення без ID сповіщення отримують гравці зі збереженою відповідною професією, але знання рецепта не підтверджене. Для замовлення з ID та ще не зчитаного рецепта сповіщення не буде. Збережені дані можуть застаріти: майстрам слід відкрити свої професії для зчитування. У вікні замовлень кнопка «Нові» вимикає лише повідомлення про нові замовлення; важливі зміни власних замовлень залишаються ввімкненими. `/okr alerts workshop` показує приклад банера, який можна перетягнути. Прострочене замовлення в роботі позначається окремо; замовник може скасувати його або підтвердити перевідкриття на 24 години, що знімає майстра та очищує відгуки. Механізм замовлень потребує перевірки у WoW Forever на двох клієнтах.

## Гільдійні події — перша версія

Відкрийте календар кнопкою «Події» в ростері або командою `/okr events` (також `/okr calendar`). Можна створити рейд, підземелля, PvP або збір гільдії, зазначити назву, опис і кількість місць, вибрати дату в календарі, а години й хвилини — у випадаючих списках. Час вибирається і показується за місцевим часом комп'ютера кожного гравця. Гравець може подати заявку з роллю або відкликати її. Автор бачить заявки й може приймати, відхиляти або переносити гравців у резерв; кількість місць обмежує лише прийнятих. Список подій має сторінки. Кошик біля власної події після підтвердження скасовує її, прибирає зі списку та сповіщає учасників.

Для події підземелля або рейду можна вибрати конкретну локацію зі списку; вона передається разом із подією. Картки подій і пошук груп використовують спільні зображення: для рейдів Barrow Deeps, Hyjal Summit і Onyxia's Lair — скриншоти з гри, для підземель — ігрові зображення. Для локацій без окремого зображення показано загальне. Біля танка, лікаря та DPS у складі показано значки ролей. У пошуку груп вибір і фільтр також підтримують рейди; доступність самих рейдів у грі потрібно перевіряти окремо.

Про нову подію іншого учасника гільдії повідомляють банер, чат і звук, якщо він доступний; клік по банеру відкриває подію. Кнопка «Сповіщення» у календарі окремо вмикає або вимикає ці повідомлення та зберігає вибір. Банер можна перетягнути; `/okr alerts event` показує приклад для налаштування позиції. Відновлення старих подій при синхронізації не показує нових сповіщень. Усі учасники мають оновити аддон; пропущені офлайн сповіщення не відтворюються.

Автор події отримує банер, повідомлення в чаті та звук, коли інший гравець успішно записується на подію. Банер показує ім'я і роль; клік відкриває подію. Повторна доставка запису не створює повторного сповіщення. Сповіщення про записи працюють незалежно від перемикача повідомлень про нові події.

Статуси заявок, склад і скасування раніше відомої події можуть передавати інші члени гільдії, які отримали цей стан безпосередньо від автора та зберегли у своєму аддоні. Хоча б один із них має бути онлайн під час синхронізації; непрямі повідомлення повторно не передаються. У деталях події вказано, коли стан отриманий через гільдію. Записи зберігаються до двох днів після запланованої події. Рішення автора та стан заявки можуть оновлюватися із затримкою.

Пересилання стану довіряє учасникам гільдії: транспорт не має криптографічного підтвердження автора в повідомленні від посередника. Аддон приймає стан лише для раніше відомої події з відповідними незмінними полями та новішою версією; пряме повідомлення автора має пріоритет за умови, що воно не старіше останнього безпосередньо отриманого від автора стану. Повністю виключити підробку учасником гільдії цей механізм не може.

Усі учасники повинні мати версію аддона з календарем та бути в одній гільдії. Автор зберігає власні події, підтверджує записи і поширює їх через гільдійний транспорт `OLDKRKN`. Запис очікує підтвердження, якщо автор не в мережі; після його повернення аддон повторює запити. Синхронізація не гарантує миттєвої доставки: автор має бути онлайн з увімкненим аддоном, щоб передати свої події новому клієнту. Минулі події прибираються через два дні, межа знімка — 2560 байтів.

Це окремий календар аддона: він не створює події у вбудованому календарі гри. Інтерфейс і обмін ще потребують перевірки на двох реальних клієнтах WoW Forever 1.60.1.

Можливу майбутню архітектуру зовнішнього сховища описано в [документі про гільдійні події](docs/EVENTS_EXTERNAL_STORAGE.md). Сервер і програма-супутник наразі не реалізовані.

## Експериментальний транспорт Group Finder

Group Finder, календар і Майстерня використовують протокол `GF2^TYPE^ID^PART^COUNT^HEX`, де HEX кодує байти payload, зокрема UTF-8. Типи Group Finder: ANNOUNCE, CANCEL, JOIN, RESPONSE, UPDATE, QUERY, SYNC, BUMP; календаря: CEVENT, CVNEW, CVSTATE, CVCANCEL, CEVQUERY, CEVRSVP; Майстерні: WKPROF, WKQUERY, WKRELAY, WRQUERY, WRRESULT, WRBATCH, WRLEARN, WRFORGET, WRQ, WRIDX, WRGET, WRPAGE, WORDER, WORELAY, WOREQ, WOPAY, WOERROR, WOQUERY, WOACT, WOPAYR, WORESULT, WORESR. Payload обмежено 2560 байтами і 32 частинами. `SendProtocol` повертає успіх лише при додаванні до черги, а не підтвердження доставки. Модель перевіряє відправника, власника та вміст повідомлення; для пересланих повідомлень діє обмеження довіри, описане вище.

Частини складаються незалежно від порядку; незавершені повідомлення та кеш дублікатів обмежено за розміром і часом. `RequestSync` ставить QUERY у чергу, після чого автори поступово передають власні знімки. Підтвердження доставки не реалізовано; дані можуть тимчасово застарівати. Черга зберігає обмеження 50, а на throttle/lockdown робить не більше п'яти спроб. `/okr comm status` показує лічильники; старий TEST/ACK збережений.

Інтерфейс Group Finder доступний через `/okr group`. Картки показують категорію або підземелля, автора, рівні, зайняті місця та частину складу; виберіть картку для перегляду повного складу і дій. Списки з багатьма групами та склад рейду можна переглядати посторінково або прокручувати. Інструкції наведено в [TESTING.md](TESTING.md). За повідомленням користувача, гільдійний Group Finder перевірено в грі й він працює добре; не всі сценарії та крайові випадки вважаються підтвердженими.

Картки використовують зображення екранів завантаження клієнта; якщо окреме зображення не задано, показується загальне. Для підземелля передбачено п'ять місць: танк, лікар і три DPS; натискання вільного місця подає заявку на його роль. Для рейдів склад гнучкий, а останній кружечок відкриває вибір ролі для запису на вільне місце. Роль обов'язкова для нових оголошень та заявок. Повний склад і кількість залишаються в деталях; роль гравця, запрошеного поза аддоном, може бути невідомою.

Автор відкритого оголошення може натиснути «Оновити набір», щоб повторно сповістити гільдію; повтор доступний раз на п'ять хвилин на оголошення протягом сеансу. Банер показує кількість учасників, відомі ролі та вільні місця. Для підземель він також показує вільні ролі. Після прийняття заявка автоматично зникає з «Моїх заявок». Кнопка видалення відкликає заявку, що очікує, або прибирає відхилений чи закритий запис з локального списку.

Під час створення оголошення категорії «Підземелля» можна вибрати українську назву з англійським скороченням. Вибір заповнює рекомендовані мінімальний і максимальний рівні, які можна змінити вручну. Обране підземелля синхронізується разом з оголошенням і доступне як окремий фільтр. Пошук за назвою або автором доповнює фільтри рівня, категорії, ролі та вільних місць. Назви, скорочення й рівні нових підземель Forever потребують уточнення в грі.

Кнопка Old Kraken біля мінікарти відкриває або закриває ростер лівим кліком і пошук груп правим. Обидва вікна також закриваються клавішею Esc. Кнопку можна перетягнути навколо мінікарти; позиція зберігається. Команди `/okr` і `/okr group` відкривають відповідні вікна.

Нові групи учасників гільдії з'являються у сповіщенні на екрані та в чаті зі звуком, якщо він доступний. Клацання по сповіщенню відкриває пошук груп. Кнопка «Сповіщення» у вікні `/okr group` вмикає або вимикає ці повідомлення; вибір зберігається. Старі записи, отримані під час синхронізації, не викликають сповіщення.

Нова заявка з'являється як сповіщення та у правій панелі пошуку груп; там можна прийняти чи відхилити заявки з усіх власних відкритих оголошень. Панель відкривається кнопкою «Заявки», а «До деталей» повертає до оголошення. Сповіщення про заявки працюють незалежно від налаштування сповіщень про групи.

Банери оголошень та заявок можна перетягнути мишею; їхні позиції зберігаються окремо. Щоб налаштувати їх без очікування події, введіть `/okr alerts group` або `/okr alerts request`. Відхилення заявки використовує позицію сповіщень про заявки.

Розумні сповіщення (увімкнено за замовчуванням у розділі `Налаштування → Сповіщення`) автоматично приглушують фонові банери й звуки у підземеллях і рейдах (`party`/`raid`) та приховують усі банери під час бою, залишаючи текстовий лог у чаті. Заявки до власних груп, що надійшли під час бою, перевіряються на актуальність після виходу з бою та показуються одним узагальненим банером (`Нові заявки: N`). Виклики `/okr alerts ...` обходять фільтр інстансу, але не показують банер під час бою. Вимкнення параметра повністю повертає попередню поведінку.

Сповіщення про групу підтримує оновлення живого складу, поки банер відкритий: після зміни оголошення зайняті ролі оновлюються, зайняті кружечки вимикаються, а лічильник учасників і вільних місць перераховується. Якщо місце стало зайнятим після показу банера, застарілий клік не повинен подавати заявку на інше місце. Закрита або недоступна група прибирає банер. Автоматизовані UI-перевірки цього сценарію є в `tests/test_alert_live_roster.py`; реальну взаємодію та доставку повідомлень усе одно потрібно перевіряти у грі.

Заявник отримує сповіщення, коли автор відхиляє саме його заявку. Клік по сповіщенню відкриває відповідне оголошення у вкладці «Мої заявки». Повторне отримання того самого рішення не показує сповіщення повторно.

Після натискання «Прийняти» аддон намагається запросити заявника в паті через `C_PartyInfo.InviteUnit`. Гра визначає, чи дозволене запрошення; якщо API недоступний або виклик завершився помилкою, запросіть гравця вручну. Сам факт виклику не гарантує доставки запрошення.

Автор оголошення автоматично синхронізує з гільдією фактичний склад паті або рейду (до 40 персонажів), зокрема гравців, запрошених поза аддоном. Прийняті заявники зберігають резерв до приєднання; коли раніше присутній учасник виходить, місце звільняється. Якщо імена ще недоступні, попередній склад зберігається до наступної спроби. Кожне відкрите оголошення автора відображає його поточну ігрову групу.

У складі біля кожного імені показано «автор», «у групі» або «резерв». Якщо аддон автора ще не визначив склад, показано «невідомо». Учасник із невідомою роллю, наприклад запрошений поза аддоном, відображається на картці знаком питання в кружку. Для синхронізації усім потрібна оновлена версія `alpha`.

Ліміт одного знімка оголошення — 2560 байтів, включно з назвами, описом та іменами. Якщо він перевищений, оновлення складу не надсилається і `/okr group status` показує причину; скоротіть назву або опис. Дуже довгі імена великого рейду також можуть перевищити ліміт.

Щоб повторно запросити гравця з резерву, автор обирає своє оголошення та натискає «Запросити» біля його імені у складі. Список складу можна прокручувати. Запрошення можна повторити, поки місце залишається в резерві.

Кнопка «×» біля учасника видаляє резерв або намагається виключити учасника з ігрової групи після підтвердження. Для виключення потрібні права лідера та підтримка `C_PartyInfo.UninviteUnit` у клієнті; склад оновлюється після фактичного виходу гравця. Дозволи і поведінка API в рейді потребують перевірки в грі.

Україномовний аддон для керування гільдійними даними та активностями у WoW Forever.

## Статус

Стабільний реліз у `main` — **`0.5.3`**, гілка подальшої розробки `alpha` — **`0.5.4-alpha.1`**, interface — `16001`, SavedVariables — `OldKrakenDB`. Усі 36 автоматизовані тести (`tests/test_*.py`) проходять локально на Lua 5.1 runtime (`lupa`).

Ідентичність включає ім'я та прізвище персонажа з обох значень `UnitName("player")`. Групи, Івенти, Ростер і Майстерня перевірені в реальній грі; протокол не має криптографічної автентифікації відправника, тому рішення приймаються з перевіркою sender-authority.

## Цілі MVP

- **Guild Roster** — перегляд і робота з гільдійним ростером.
- **Group Finder** — пошук гравців для груп.
- **Events / Calendar** — планування гільдійних подій.
- **WoW Hub** — додаткове джерело для імпорту або звірки даних ростера.

## Перевірено в WoW Forever 1.60.1 (70938)

У клієнті підтверджено:

- `GetBuildInfo()` повертає interface number `16001`.
- `C_GuildInfo.GuildRoster()`, `GetGuildRosterInfo()` та `GetNumGuildMembers()` доступні.
- `GUILD_ROSTER_UPDATE` спрацьовує після запиту оновлення ростера.
- `C_Calendar` та `C_Calendar.GetEventInfo` доступні.
- `C_ChatInfo.SendAddonMessage` доступна, але `AreOutgoingAddonChatMessagesRestricted()` повертає `true` у перевіреному клієнті.

Наявність функцій не гарантує доступність усіх операцій. Календар і обмін аддон-повідомленнями потребують окремих функціональних тестів.

## Communication diagnostics

- `Communication.lua` додає окремий транспортний шар для guild addon messages.
- Префікс: `OLDKRKN`; канал: `GUILD`.
- Вихідні повідомлення проходять через чергу з повторною спробою при throttle/lockdown.
- Вхідні повідомлення приймаються через `CHAT_MSG_ADDON`.
- `/okr comm status` показує доступність API, реєстрацію префікса та стан обмеження вихідних повідомлень.
- `/okr comm test` надсилає тестове повідомлення; клієнти з аддоном автоматично відповідають ACK. Успішний ACK підтверджує двосторонню доставку між клієнтами.
- Значення `AreOutgoingAddonChatMessagesRestricted()` виводиться як діагностика, але не блокує спробу відправлення: остаточний результат визначається функціональним тестом.
- Потрібно перевірити на двох персонажах/клієнтах у гільдії. До цього спільна синхронізація не вважається підтвердженою.

## Native Group Finder API discovery

У клієнті WoW Forever 1.60.1 (70938), Interface `16001`, попередні внутрішньоігрові перевірки підтвердили:

- `C_LFGList` і `C_LFGInfo` — таблиці.
- `C_LFGList.GetAvailableActivities`, `GetSearchResults`, `GetSearchResultInfo`, `Search`, `CreateListing` і `UpdateListing` — функції.
- `C_LFGList.RequestToJoin` — `nil`.
- `LFGListFrame` — `nil`. Це означає лише, що саме цей глобальний frame відсутній; це не доводить відсутність усього Group Finder UI.

Ще не підтверджено безпосередньо в цьому клієнті: `GetAvailableCategories`, `GetActivityInfoTable`, `GetSearchResultPlayerInfo`, `ApplyToGroup`, `IsPremadeGroupFinderEnabled`, фактичні результати пошуку та створення оголошення.

Документація API для flavor Camelot / Forever 1.60.1 описує:

- `Search(categoryID, filter, preferredFilters, languageFilter?, searchCrossFactionListings?, advancedFilter?, activityIDsFilter?)`.
- Подію `LFG_LIST_SEARCH_RESULTS_RECEIVED`; `GetSearchResults()` повертає загальну кількість і масив ID.
- `GetSearchResultInfo(resultID)` повертає дані оголошення; `GetSearchResultPlayerInfo(resultID, memberIndex)` — дані учасника.
- `CreateListing` і `UpdateListing` приймають структуру `LfgListingCreateData`.

Важливі обмеження: документація позначає `Search` та `CreateListing` як restricted у певних ситуаціях. `ApplyToGroup` у довіднику позначений як припущений метод, відсутній у Blizzard API docs. Тому цей код не викликає `Search`, `ApplyToGroup`, `CreateListing` чи `UpdateListing` і не робить припущень щодо їхньої доступності/безпечного виклику.

Команда `/okr group api` виконує лише read-only перевірку наявності методів і, якщо доступно, читає ID категорій та активностей. Це діагностичний крок, а не реалізація нативного пошуку. Поточний Group Finder Old Kraken залишається окремим гільдійним механізмом через addon messages у каналі `GUILD`.

### Малий перевірюваний MVP для нативного пошуку

1. Спочатку зібрати read-only звіт `/okr group api` та фактичні ID категорій/активностей.
2. Далі окремо перевірити безпечний спосіб запуску `Search`, подію результатів і читання одного result ID — без автоматичного створення оголошень.
3. Лише після цього додавати створення listing та заявки, коли підтверджені структура payload і метод подання заявки в реальному клієнті.

Джерела: [C_LFGList для Camelot](https://wowlua.dev/api/C_LFGList), [Search](https://wowlua.dev/api/C_LFGList/Search), [GetSearchResults](https://wowlua.dev/api/C_LFGList/GetSearchResults), [GetSearchResultInfo](https://wowlua.dev/api/C_LFGList/GetSearchResultInfo), [GetSearchResultPlayerInfo](https://wowlua.dev/api/C_LFGList/GetSearchResultPlayerInfo), [CreateListing](https://wowlua.dev/api/C_LFGList/CreateListing).

## Guild Roster

- Пошук за ім'ям персонажа.
- Перемикання фільтра статусу: усі / онлайн / офлайн.
- Випадаючий список вибору класу, включно з пунктом «Усі класи».
- Сортування кліком по заголовках: ім'я, ранг, рівень, клас і локація.
- Сортування за локацією — за назвою з урахуванням регістру; повторний клік змінює напрямок.
- Онлайн-учасники завжди відображаються першими.
- Сортування за замовчуванням: рівень за зростанням усередині групи онлайн/офлайн.
- Імена та назви класів використовують кольори класів WoW, якщо вони доступні в клієнті.
- Лічильник показує повний склад, кількість онлайн і кількість записів після фільтрації.
- Пошук, фільтри й сортування зберігаються через SavedVariables.

## Джерела даних

- Ігровий гільдійний ростер є основним джерелом актуального складу, рівнів і рангів.
- WoW Hub розглядається як допоміжне джерело. Спосіб отримання та формат імпорту ще потрібно дослідити.

## Архітектура та обмеження

- Самостійний аддон на Lua/XML.
- Початковий етап — без власного backend-сервера.
- Для локальних даних використовується механізм WoW SavedVariables.
- Обмін addon messages у каналі GUILD має діагностичний TEST/ACK; користувач також підтвердив базову видимість оголошень на двох клієнтах після виправлення sender identity. Значення AreOutgoingAddonChatMessagesRestricted() залишається діагностичним сигналом, а не самостійним доказом доставки.
- Зовнішні HTTP-запити з аддону не вважаються доступними без підтвердження API клієнта.

## Поточна структура

Модулі перелічено в порядку завантаження з `OldKraken.toc`:

```
OldKraken.toc                — список файлів аддона; його читають і workflows пакування
Database.lua                 — схема та міграції OldKrakenDB
Locale.lua                   — вибір мови та таблиця англійських перекладів
Core.lua                     — життєвий цикл, шина подій, спільний UI-стиль
UIHub.lua                    — каркас вікна та реєстрація сторінок
Communication.lua            — транспорт GUILD-повідомлень
GuildRoster.lua              — ростер гільдії
ActivityCatalog.lua          — спільний каталог підземель і рейдів для подій та груп
GroupFinder.lua              — модель оголошень, заявок і рішень
GroupFinderIntegration.lua   — прив'язка до гільдії й поточної групи, збереження стану
GroupFinderUI.lua            — вікно гільдійного Group Finder
GroupFinderAPI.lua           — read-only діагностика нативного C_LFGList
GuildEvents.lua              — календар гільдійних подій
Workshop.lua                 — каталог професій і майстрів
WorkshopRecipes.lua          — пошук і зчитування рецептів
WorkshopSync.lua             — версійовані знімки рецептів
WorkshopOrders.lua           — замовлення та їхній життєвий цикл
WorkshopDeliveries.lua       — спостереження за підтвердженим обміном і поштою
Minimap.lua                  — кнопка біля мінікарти
Media/                       — герб аддона та зображення рейдів
docs/                        — проєктні документи (зовнішнє сховище подій)
tests/                       — Python-тести на Lua 5.1 через Lupa
.github/workflows/           — перевірка та пакування
README.md
TESTING.md
LICENSE
```

### Ініціалізація та локальні дані

- `Database.lua` — єдине місце ініціалізації `OldKrakenDB`, значень за замовчуванням і версії схеми `schemaVersion`.
- `Core.lua` — життєвий цикл аддона, внутрішні події `OldKraken:On()` / `OldKraken:Fire()` і спільний стиль `OldKraken.UIStyle`.
- `UIHub.lua` — спільне вікно аддона: сторінки реєструються через `UIHub:RegisterPage()` і створюються ліниво.
- `Communication.lua` — діагностичний транспорт обміну addon messages у каналі `GUILD`.
- `GuildRoster.lua` — інтерфейс і робота з ігровим API ростера; налаштування читаються з `OldKraken.DB.settings.roster`.
- `ActivityCatalog.lua` — українські назви підземель і рейдів, рекомендовані рівні, іконки ролей і зображення; спільний для календаря та Group Finder.
- `GroupFinder.lua` — модель оголошень, заявок, рішень і версійованої синхронізації.
- `GroupFinderIntegration.lua` — прив’язка до гільдії/поточної групи, sender identity та збереження Group Finder у SavedVariables.
- `GroupFinderUI.lua` — вікно гільдійного Group Finder.
- `GroupFinderAPI.lua` — read-only діагностика нативного `C_LFGList`; не запускає пошук і не створює listing.
- `GuildEvents.lua` — календар подій; автор події є джерелом істини для складу й заявок.
- `Workshop.lua` — каталог професій і майстрів; кожен персонаж публікує лише власний знімок.
- `WorkshopRecipes.lua` — пошук і зчитування рецептів; відфільтрований скан ніколи не вважається повним списком.
- `WorkshopSync.lua` — версійовані знімки рецептів; ретранслюються лише отримані безпосередньо від власника.
- `WorkshopOrders.lua` — замовлення; замовник є джерелом остаточного стану.
- `WorkshopDeliveries.lua` — спостереження за підтвердженим обміном і поштою; сам не ініціює ні обмін, ні відправлення.
- `Minimap.lua` — кнопка Old Kraken біля мінікарти, кут зберігається в `OldKraken.DB.settings.minimapAngle`.
- Існуючі таблиці `settings`, `roster` та `events` зберігаються під час ініціалізації. Нові поля додаються без очищення наявних даних.
- Поточна схема БД — `3`. Поле `version` залишається версією аддона, а `schemaVersion` використовується для міграцій структури даних.

## Використання

- `/okr` або `/oldkraken` — відкрити вікно ростера.
- Кнопка **Оновити** — запросити оновлення ростера.
- Поле пошуку — фільтрувати за ім'ям.
- Випадаючий список **Статус** — вибрати усі / онлайн / офлайн.
- Випадаючий список **Клас** — вибрати конкретний клас або «Усі класи».
- Клік по заголовках **Ім'я**, **Ранг**, **Рів.**, **Клас**, **Локація** — змінювати сортування та напрямок.
- `/okr refresh` — запросити оновлення без відкриття вікна.
- `/okr comm status` — перевірити стан транспорту.
- `/okr comm test` — надіслати тестове повідомлення членам гільдії.
- `/okr group api` — read-only діагностика нативного Group Finder API.
