# Перевірка Old Kraken Group Finder

Ця гілка є тестовою. Перевірка двома реальними клієнтами WoW Forever 1.60.1 ще потрібна. На обох клієнтах має бути однакова версія аддона та персонажі однієї гільдії.

Перед встановленням збережіть копії поточної папки `OldKraken` за межами `Interface/AddOns` та файлу SavedVariables `OldKraken.lua` у `WTF` (або всієї папки `WTF`). Тестова версія оновлює схему SavedVariables до 2. Скопіюйте всі файли з гілки всередину `Interface/AddOns/OldKraken`, зберігши назву папки та файл `OldKraken.toc`. Не встановлюйте архів поверх незбережених локальних змін Git.

## Команди в грі

| Команда | Призначення |
| --- | --- |
| `/reload` | Перезавантажити інтерфейс після встановлення. |
| `/console scriptErrors 1` | Увімкнути показ Lua-помилок. |
| `/okr` або `/oldkraken` | Відкрити наявний ростер гільдії. |
| `/okr refresh` | Запросити оновлення ростера. |
| `/okr comm status` | Показати стан реєстрації префікса, черги та лічильники транспорту. |
| `/okr comm test` | Надіслати тест TEST/ACK іншому клієнту. |
| `/okr group` або `/okr groups` | Відкрити тестовий пошук груп. |
| `/okr group sync` | Надіслати запит синхронізації вручну. |
| `/okr group status` | Показати ідентичність, останнього відправника та статистику приймання оголошень. Лічильник «не додано» включає звичайні повтори. |

Group Finder використовує обидва значення `UnitName("player")`, з'єднані пробілом, як повне ім'я, і перевіряє його точну відповідність `sender`. Наприклад, `Hok Mon` і `Hok Moon` — різні персонажі; значення `GetRealmName()` не є прізвищем персонажа. Після входу виконайте `/okr group sync` і перевірте `/okr group status`. Обидва клієнти мають використовувати цю версію; старі короткі імена несумісні з повними.

Дані з неоднозначними короткими іменами не слід використовувати для визначення персонажа. Перед оновленням збережіть копію SavedVariables.

## Сценарії для двох гравців

1. На обох клієнтах увімкніть Lua-помилки та перевірте `/okr comm status`. Виконайте `/okr comm test` по черзі на кожному; інший клієнт має отримати TEST, а відправник — ACK. Занотуйте точні імена у повідомленнях і обидва результати `/dump UnitName("player")` на кожному клієнті. Вони мають збігатися з повним sender, розділені одним пробілом.
2. На клієнті A відкрийте `/okr group`, вкладку «Створити», введіть назву, опис, категорію, кількість місць і діапазон рівнів та натисніть «Створити». На B оголошення має з’явитися у «Усі групи». Перевірте категорію, роль, рівень та фільтр вільних місць.
3. На B виберіть оголошення, роль та «Подати заявку». На A виберіть оголошення у «Мої оголошення»: ім’я та роль заявника мають з’явитися в списку заявок. Натисніть «Прийняти» біля потрібного імені. Склад і число місць мають оновитися на обох, а стан заявки B — змінитися на «Прийнято». Якщо заявок більше чотирьох, перегляньте наступну сторінку стрілками під списком.
4. Для окремого оголошення перевірте «Відхилити»; для іншої заявки — «Відкликати». Перевірте, що відповідний стан або список заявок змінився на обох клієнтах. Перевірте видалення учасника та редагування оголошення автором.
5. Перезавантажте інтерфейс на B (`/reload`). Поки A залишається онлайн, оголошення має відновитися після періодичного запиту; зачекайте щонайменше три хвилини з урахуванням черги. Перевірте повторний вхід A та відновлення його власних оголошень.
6. На A натисніть «Закрити набір» і перевірте, що оголошення зникає зі списку відкритих на B. Повторіть тест з одночасними заявками та перевірте, що ліміт місць не перевищений.
7. Повторіть `/okr` і `/okr comm test`, щоб перевірити наявні ростер та TEST/ACK. Зафіксуйте Lua-помилки, обидва імені, команди та порядок дій.

### Ідентичність і відновлення відхиленої заявки

- На кожному клієнті виконайте `/dump GetBuildInfo()` і `/dump UnitName("player")`. Переконайтеся, що build — `70938`, а interface — `16001`. Порівняйте обидва значення `UnitName` із фактичним `sender` у повідомленні TEST на іншому клієнті. Якщо оголошення не проходить, запишіть ці значення та результат `/okr group status`.
- B подає заявку, потім виходить із гри. A відхиляє заявку, робить `/reload` або виходить у меню персонажів та заходить знову. B повертається в гру. Поки A онлайн, стан заявки B має відновитися як «Відхилено» після запиту синхронізації. Дочекайтеся до трьох хвилин і врахуйте зайнятість черги.
- B подає нову заявку на те саме оголошення. Старе відхилення не повинне змінити стан нової заявки. Перевірте й повторне надходження повідомлень після `/reload`, а також відмову/відкликання в обох порядках.
- Якщо перевірка не проходить, зафіксуйте `/okr comm status` на обох клієнтах, точний порядок дій і Lua-помилку. Рішення зберігаються у SavedVariables і фізично записуються грою під час `/reload` або штатного виходу; раптове завершення клієнта може втратити останні зміни.

У разі розбіжностей не вважайте стан синхронізованим лише за повідомленням про додавання пакета в чергу. Відправлення не гарантує доставку. Прийняття заявки запускає спробу запрошення через ігровий API, але не гарантує доставку або вступ гравця.

## Рейд і склад для перевірки згодом

- На оновлених клієнтах створіть рейдове оголошення та переведіть паті автора в рейд. Порівняйте імена і статуси в оголошенні з ігровим рейдом на обох клієнтах; перевірте автора, учасників різних підгруп і запрошеного поза аддоном.
- Додайте та приберіть учасника, перевірте місця, оновлення на обох клієнтах та збереження резервів, які ще не вступили. Перевірте вихід офлайн-учасника, `/reload`, перехід рейд → паті → соло та повторну синхронізацію.
- Перевірте повторне запрошення резерву та виключення з підтвердженням лідером і гравцем без потрібних прав. Підтвердіть, що фактичний склад змінюється лише після відповіді гри.
- Зафіксуйте результати `/dump UnitName("raid1")`, `/dump GetNumGroupMembers()`, `/okr group status` та Lua-помилки. Формат повних імен учасників рейду і поведінку API в цьому клієнті ще не підтверджено.
- Для великого складу та довгого опису перевірте обмеження 2560 байтів і чергу: при перевищенні має з'явитися повідомлення, попередній склад має залишитися цілим.

## Локальні тести (Linux / Bazzite)

Потрібні Python 3 та `venv`. Із кореня клонованого репозиторію:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install lupa==2.8
for test in tests/test_*.py; do
  python "$test" || exit 1
done
```

На Bazzite це не змінює системний Python: залежність встановлюється лише у `.venv`.

Це тести із заглушками API та симуляцією клієнтів; вони не підтверджують сумісність інтерфейсу чи API в реальній грі.
