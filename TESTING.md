# Перевірка Old Kraken Group Finder

Ця гілка є тестовою. Користувач уже підтвердив базову видимість оголошень між двома клієнтами після виправлення sender identity; повний цикл заявок, відновлення, рейду та запрошень ще потрібно перевірити. На обох клієнтах має бути однакова версія аддона та персонажі однієї гільдії.

Перед встановленням збережіть копії поточної папки `OldKraken` за межами `Interface/AddOns` та файлу SavedVariables `OldKraken.lua` у `WTF` (або всієї папки `WTF`). Тестова версія оновлює схему SavedVariables до 3. Скопіюйте всі файли з гілки всередину `Interface/AddOns/OldKraken`, зберігши назву папки та файл `OldKraken.toc`. Не встановлюйте архів поверх незбережених локальних змін Git.

## Команди в грі

| Команда | Призначення |
| --- | --- |
| `/reload` | Перезавантажити інтерфейс після встановлення. |
| `/console scriptErrors 1` | Увімкнути показ Lua-помилок. |
| `/okr` або `/oldkraken` | Відкрити наявний ростер гільдії. |
| `/okr refresh` | Запросити оновлення ростера. |
| `/okr comm status` | Показати стан реєстрації префікса, черги та лічильники транспорту. |
| `/okr comm test` | Надіслати тест TEST/ACK іншому клієнту. |
| `/okr group` або `/okr groups` | Відкрити тестовий пошук груп. |
| `/okr group sync` | Надіслати запит синхронізації вручну. |
| `/okr group status` | Показати ідентичність, останнього відправника та статистику приймання оголошень. Лічильник «не додано» включає звичайні повтори. |
| `/okr group api` | Read-only перевірити нативні API Group Finder, а також списки ID категорій і активностей, якщо вони доступні. Пошук і створення не запускаються. |

Group Finder використовує обидва значення `UnitName("player")`, з'єднані пробілом, як повне ім'я, і перевіряє його точну відповідність `sender`. Наприклад, `Hok Mon` і `Hok Moon` — різні персонажі; значення `GetRealmName()` не є прізвищем персонажа. Після входу виконайте `/okr group sync` і перевірте `/okr group status`. Обидва клієнти мають використовувати цю версію; старі короткі імена несумісні з повними.

Дані з неоднозначними короткими іменами не слід використовувати для визначення персонажа. Перед оновленням збережіть копію SavedVariables.

## Native Group Finder API probe (read-only)

1. Виконайте `/okr group api` після входу у світ.
2. Переконайтеся, що команда не викликає Lua-помилки. Вона показує типи `C_LFGList`, `C_LFGInfo`, `LFGListFrame`, наявність методів та ID категорій/активностей, якщо відповідні функції повертають таблиці.
3. Перевірте, що наприкінці виведено: `Search / CreateListing / UpdateListing не викликалися.` Команда не створює оголошень і не запускає пошук.
4. Збережіть повний результат команди для наступного етапу. Якщо категорії або активності позначено як недоступні/помилка — зафіксуйте саме цей рядок.

Не викликайте `C_LFGList.Search` або `CreateListing` вручну під час цієї перевірки. Для `Search` ще треба окремо перевірити дозволений secure-виклик і подію результатів; для створення — структуру даних і фактичну відповідь клієнта. Наявність функції через `type(...)` сама по собі не підтверджує успішну операцію.

## Сценарії для двох гравців

1. На обох клієнтах увімкніть Lua-помилки та перевірте `/okr comm status`. Виконайте `/okr comm test` по черзі на кожному; інший клієнт має отримати TEST, а відправник — ACK. Занотуйте точні імена у повідомленнях і обидва результати `/dump UnitName("player")` на кожному клієнті. Вони мають збігатися з повним sender, розділені одним пробілом.
2. На клієнті A відкрийте `/okr group`, вкладку «Створити», введіть назву, опис, категорію, кількість місць і діапазон рівнів та натисніть «Створити». На B оголошення має з’явитися у «Усі групи». Перевірте категорію, роль, рівень та фільтр вільних місць.
3. На B виберіть оголошення, роль та «Подати заявку». На A відкрийте «Заявки» у правій панелі: ім’я та роль заявника мають з’явитися у списку. Натисніть «Прийняти» біля потрібного імені. Склад і число місць мають оновитися на обох. Якщо заявок більше п’яти, перегляньте наступну сторінку; перевірте повернення кнопкою «До деталей».
4. Для окремого оголошення перевірте «Відхилити»; для іншої заявки — «Відкликати». Перевірте, що відповідний стан або список заявок змінився на обох клієнтах. Перевірте видалення учасника автором.
5. Перезавантажте інтерфейс на B (`/reload`). Поки A залишається онлайн, оголошення має відновитися після періодичного запиту; зачекайте щонайменше три хвилини з урахуванням черги. Перевірте повторний вхід A та відновлення його власних оголошень.
6. На A натисніть «Закрити набір» і перевірте, що оголошення зникає зі списку відкритих на B. Повторіть тест з одночасними заявками та перевірте, що ліміт місць не перевищений.
7. Повторіть `/okr` і `/okr comm test`, щоб перевірити наявні ростер та TEST/ACK. Зафіксуйте Lua-помилки, обидва імені, команди та порядок дій.

### Ідентичність і відновлення відхиленої заявки

- На кожному клієнті виконайте `/dump GetBuildInfo()` і `/dump UnitName("player")`. Переконайтеся, що build — `70938`, а interface — `16001`. Порівняйте обидва значення `UnitName` із фактичним `sender` у повідомленні TEST на іншому клієнті. Якщо оголошення не проходить, запишіть ці значення та результат `/okr group status`.
- B подає заявку, потім виходить із гри. A відхиляє заявку, робить `/reload` або виходить у меню персонажів та заходить знову. B повертається в гру. Поки A онлайн, стан заявки B має відновитися як «Відхилено» після запиту синхронізації. Дочекайтеся до трьох хвилин і врахуйте зайнятість черги.
- B подає нову заявку на те саме оголошення. Старе відхилення не повинне змінити стан нової заявки. Перевірте й повторне надходження повідомлень після `/reload`, а також відмову/відкликання в обох порядках.
- Якщо перевірка не проходить, зафіксуйте `/okr comm status` на обох клієнтах, точний порядок дій і Lua-помилку. Рішення зберігаються у SavedVariables і фізично записуються грою під час `/reload` або штатного виходу; раптове завершення клієнта може втратити останні зміни.

У разі розбіжностей не вважайте стан синхронізованим лише за повідомленням про додавання пакета в чергу. Відправлення не гарантує доставку. Прийняття заявки запускає спробу запрошення через ігровий API, але не гарантує доставку або вступ гравця.

## Рейд і склад для перевірки згодом

- На оновлених клієнтах створіть рейдове оголошення та переведіть паті автора в рейд. Порівняйте імена і статуси в оголошенні з ігровим рейдом на обох клієнтах; перевірте автора, учасників різних підгруп і запрошеного поза аддоном.
- У паті приєднайте щонайменше двох гравців і дочекайтеся позначок «у групі». Вихід одного гравця має прибрати його зі складу на обох клієнтах, а вихід останнього — автоматично видалити оголошення. Повторіть після `/reload` і з рейдом. Нове оголошення соло-автора не видаляється до того, як у його реальній паті хтось побував. Прийнятий гравець, який ще не вступив, показується як резерв.
- Додайте та приберіть учасника, перевірте місця, оновлення на обох клієнтах та збереження резервів, які ще не вступили. Перевірте вихід офлайн-учасника, `/reload`, перехід рейд → паті → соло та повторну синхронізацію.
- Перевірте повторне запрошення резерву та виключення з підтвердженням лідером і гравцем без потрібних прав. Підтвердіть, що фактичний склад змінюється лише після відповіді гри.
- Зафіксуйте результати `/dump UnitName("raid1")`, `/dump GetNumGroupMembers()`, `/okr group status` та Lua-помилки. Формат повних імен учасників рейду і поведінку API в цьому клієнті ще не підтверджено.
- Для великого складу та довгого опису перевірте обмеження 2560 байтів і чергу: при перевищенні має з'явитися повідомлення, попередній склад має залишитися цілим.

## Майстерня: професії та рецепти

Потрібні два персонажі однієї гільдії з однаковою версією Old Kraken. Це інструкція для перевірки у WoW Forever; фактичну роботу API тут ще не підтверджено.

1. Відкрийте `/okr workshop` і перевірте картки професій, їхні значки та оформлення; якщо гра не надає фон професії, має бути нейтральний фон. Відкрийте картку та перевірте вкладки «Рецепти» і «Майстри», пошук, фільтр онлайн, рівень та дату. Майстер без зчитаних рецептів має залишатися у списку, якщо відома його професія.
2. На першому персонажі відкрийте власну професію й зачекайте кілька секунд. На другому відкрийте відповідну картку в Майстерні. Перевірте появу збережених рецептів, зображення предмета, списку майстрів і матеріалів, якщо клієнт надає їхню схему. Великий список може надходити частинами з черги.
3. Натисніть «Замовити» у вікні рецепта і перевірте заповнені предмет та професію. Передача предметів і золота залишається ручною. У ростері натисніть значок професії конкретного майстра і перевірте, що відображаються його збережені рецепти.
4. Перевірте учасника без Old Kraken: якщо гра повертає його професії, значки мають бути тьмяними та без вигаданого рівня; перелік його рецептів не вважається відомим. Перевірте, чи новий рецепт і рецепти іншого персонажа акаунта з'являються після зчитування; якщо ні, відкрийте відповідну професію вручну.
5. Третій персонаж у гільдії отримує повний збережений знімок майстра безпосередньо від нього та виконує `/reload`. Майстер виходить; новий клієнт входить із порожнім кешем і запитує знімок через цього посередника. Перевірте кількість рецептів, повтор після втрати повідомлень та відновлення прямого стану майстра після його входу. Великий список може надходити довго.
6. На тестовому персонажі змініть професію після збереження її рецептів. Перевірте, що новий стан не застосовується миттєво, а після повторних зчитувань стара професія та її рецепти зникають локально і в гільдії. Перезавантажте посередника, виведіть майстра й перевірте відновлення видалень третім персонажем.
7. Перевірте рецепт, який гра явно показує невивченим: він має зникнути лише після трьох повних готових сканувань власної професії. Увімкнені фільтри, закриття вікна або неповні дані не повинні видаляти інші рецепти. Повторне вивчення і запізнілі старі повідомлення не повинні повертати неправильний стан. Перевірте позначки застарілих даних і невідомої дати.

### Облік передачі замовлення

1. Два персонажі з гілкою Майстерні створюють замовлення на відомий рецепт із ID предмета, кількістю більше одного та винагородою; замовник обирає майстра. Відкрийте деталі замовлення на обох клієнтах.
2. Передайте частину матеріалів і винагороди через торгівлю. Після підтвердження гри перевірте кількість у деталях; скасована торгівля та закриття вікна без завершення не повинні додавати прогрес.
3. Передайте вироби кількома угодами. Статус не повинен завершитися до повної кількості й підтвердження майстром усієї винагороди. Перевірте повторні події, `/reload` і два замовлення однакових предметів між тими ж персонажами.
4. Повторіть передачу поштою: надсилання, отримання вкладень і грошей, часткове отримання, помилку заповнених сумок і повторне оновлення поштової скриньки. Перевірте, що невдала або непідтверджена дія не зараховується двічі.
5. Якщо гра не повертає ID чи схему, повідомлення про успішну торгівлю або поштові дані, зафіксуйте обмеження й завершіть замовлення ручними кнопками.

## Майстерня: синхронізація через учасника гільдії

Потрібні три персонажі A (замовник), B (посередник) і C (майстер) в одній гільдії, усі з оновленим аддоном. Знімки замовлень можна ретранслювати, але вони не є доказом авторства дій. Дії та платежі не приймаються через посередника: без криптографічного підтвердження він не може довести, що заявлений актор справді надіслав пакет. Для застосування зміни власник замовлення має отримати її безпосередньо від фактичного відправника.

1. A створює замовлення через `/okr orders`. B отримує його напряму, A виходить із гри, а C через запит синхронізації отримує знімок від B. У C замовлення має бути позначене як отримане через гільдію; його відображений стан не є авторитетним.
2. Поки A офлайн, C надсилає пропозицію майстра або платіж. Переконайтеся, що B не ретранслює їх як авторитетні дії та що стан замовлення не змінюється. Після входу A зміна може застосуватися лише коли A отримає пакет безпосередньо від C; перевірте пропозицію, відмову, позначку «Передав» і платіж.
3. Перевірте, що підтвердження результату може дійти до C через B, але воно не змінює авторитетний стан замовлення. Повторіть дії та повідомлення; дубль або застаріле підтвердження не повинні застосовувати стан.
4. Перевірте ту саму пряму взаємодію, коли A і C одночасно онлайн. При проблемах запишіть порядок дій і `/okr comm status` кожного клієнта.

## Локальні тести (Linux / Bazzite)

Потрібні Python 3 та `venv`. Із кореня клонованого репозиторію:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install lupa==2.8
for test in tests/test_*.py; do
  python "$test" || exit 1
done
```

На Bazzite це не змінює системний Python: залежність встановлюється лише у `.venv`.

Це тести із заглушками API та симуляцією клієнтів; вони не підтверджують сумісність інтерфейсу чи API в реальній грі.

| Workshop sync | Пряма передача знімка рецептів, повтор сторінки, перевірка індексу/сторінки та заборона повторної ретрансляції знімка, отриманого через посередника |

Це функціональне покриття критичних контрактів, а не вимірювання 100% line/branch coverage. Якщо змінюється формат протоколу, схема SavedVariables або публічна поведінка модуля, відповідний тест слід оновити разом із кодом.

Станом на 18 листопада 2026 усі 33/33 файлів локально проходять на `0.5.3-alpha.1` (`alpha`) та `0.5.2` (`main`). Це локальна перевірка з моками API, а не заміна ручного тестування в WoW.

## Guild Events: перевірка авторитетності relay

Автоматизовані сценарії в `tests/test_events_relay_authority.py` перевіряють:
- прямий стан автора зберігається окремо від останнього ретрансльованого знімка;
- ретрансляція з більшою ревізією не блокує пізніше отриманий прямий стан автора;
- ретрансльоване скасування не створює сповіщення про скасування;
- подія, відома лише через relay, доступна лише для перегляду: подати заявку з такого стану не можна;
- payload із заявленим автором, який не збігається з фактичним sender прямого повідомлення, відхиляється.

Лічильники сесії доступні через `OldKraken.GuildEvents:GetRelayDiagnostics()`; для виводу причин відхилення без вмісту повідомлень можна виконати:
```lua
/run OldKraken.GuildEvents:PrintRelayDiagnostics()
```
Лічильники не зберігаються між перезапусками клієнта. Повні payload-и не логуються.

## Group Finder: sender та захист від повторів

У Group Finder немає ретрансляційного типу для оголошень/оновлень: знімок приймається лише коли фактичний `CHAT_MSG_ADDON sender` збігається з автором у payload. Заявка прив'язується до фактичного sender, а не до переданого імені заявника. Відповідь приймається лише від автора оголошення й для локального персонажа-заявника.

`tests/test_group_replay.py` перевіряє:
- повтор заявки після відновлення збережених `requestVersions` після перезапуску;
- повтор після видалення запису заявки, коли version fence збережений;
- що інший фактичний sender не може змінити заявку від імені попереднього заявника;
- відхилення оголошення з підробленим sender.

`requestVersions` є окремим від транспортного кешу дедуплікації: транспортний кеш живе лише в пам'яті, а version fence заявки зберігається у SavedVariables. Для відкритого оголошення його не очищати: інакше старий пакет після втрати кешу знову стане прийнятним. Після закриття оголошення `Prune()` безпечно очищає пов'язані заявки, рішення та version fence, оскільки закритий tombstone відхиляє будь-який повтор незалежно від версії.

### Живий склад у сповіщенні Group Finder

Автоматизований тест `tests/test_alert_live_roster.py` перевіряє UI-контракт відкритого банера групи:
- зміна складу оновлює зайняті ролі та лічильник учасників/вільних місць без перезапуску часу життя банера;
- зайнятий слот вимикається; застарілий клік по ньому не створює заявку на інший слот тієї самої ролі;
- звільнений слот знову стає доступним після нового оновлення;
- заміна об'єкта оголошення новим знімком також оновлює відкритий банер;
- заповнена або закрита група не залишає доступних слотів, а закриття прибирає банер;
- повторні події оновлення не створюють необмежено нових UI-об'єктів.

**Ручна перевірка у WoW (два клієнти):**
1. На A створіть підземельне оголошення з вільними ролями; на B дочекайтеся банера й перевірте початковий склад та лічильник.
2. На A прийміть заявку або додайте учасника так, щоб одне з місць у банері B стало зайнятим. Переконайтеся, що банер B оновився без повторного показу/перезапуску таймера, а зайнятий слот більше не натискається.
3. На B спробуйте натиснути слот, який став зайнятим після появи банера. Переконайтеся, що заявка не подається на інший слот тієї самої ролі.
4. На A звільніть місце та перевірте, що після отримання оновлення відповідний слот знову доступний на B.
5. Заповніть групу або закрийте оголошення на A. Банер B має показати нуль вільних місць або зникнути для закритої групи.
6. Повторіть із оновленням знімка, отриманим від іншого клієнта, та після штатного `/reload`. Зафіксуйте обидва `/okr group status`, Lua errors і фактичну поведінку банера.

CI підтверджує поведінку тестової UI-моделі, але не фактичну доставку addon messages або рендеринг у WoW Forever.


### Guild Events: вибір активності та запрошення на рейд

Автоматизований сценарій `tests/test_event_raid_invites.py` перевіряє вибір активності рейду/підземелля та запрошення учасників події:
- вибір локації підставляє її назву в заголовок події; картки активностей можна переглядати зі прокручуванням без створення нових UI-карток при повторному відкритті;
- автор події може запускати індивідуальні або масові запрошення лише для прийнятих учасників, які ще не перебувають у групі;
- у звичайній групі черга спочатку запрошує не більше чотирьох учасників, потім намагається перетворити групу на рейд і продовжує запрошення;
- запрошення призупиняються під час бою; перевіряються права лідера/помічника, власник і стан події, дублікати та вже згруповані персонажі.

Це тестування з підставними API через Lupa. Реальні запрошення, перетворення групи на рейд, обмеження клієнта та права в WoW Forever потрібно окремо перевірити в грі.

### Ручний тест relay у Guild Events (A — автор, B — прямий отримувач, C — отримувач через B)

1. A створює подію. Переконайтеся, що B отримав її напряму.
2. C входить у гільдію та запитує синхронізацію. B має передати збережений знімок через `CVSTATE`; C бачить подію з позначкою «Стан отримано через гільдію».
3. На C перевірте, що кнопки подачі заявки/виходу недоступні. Спробуйте викликати `Events:Signup` через Lua — операція має повернути `false`.
4. A змінює склад/статус або опис події. Після прямого повідомлення від A C має показати прямий стан без позначки relay.
5. A скасовує подію. Сповіщення про скасування має надходити з прямого повідомлення автора, не з relay.
6. Повторіть після штатного `/reload` на B і C. Переконайтеся, що SavedVariables зберігають прямий та relay стани окремо.

Ці кроки перевіряють реальну доставку й UI, чого CI не підтверджує.

## Межі автоматизованих тестів

Тести працюють із заглушками API та симульованими Lua-клієнтами. Вони **не можуть підтвердити**:
- фактичну сумісність усіх WoW Forever API та UI-віджетів у build 70938;
- поведінку захищених дій, запрошень, рейдових операцій і реальних trade/mail-подій;
- реальну доставку GUILD addon messages, throttling, затримки та втрати на сервері;
- повноту зчитування рецептів із живої книги професій;
- взаємодію двох/трьох запущених клієнтів у грі.

Для цих пунктів обов'язковий ручний чекліст вище. У звіті про реліз автоматизовані результати й ручні результати потрібно позначати окремо.
